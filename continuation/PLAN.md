# Инвентаризация и план дописывания

## Исходная база (прочитана до реализации)

Файлы перечислены с размерами и SHA-256 в `evidence/inventory.json`.

| Имеющийся код | Содержание и граница |
|---|---|
| `src/nl_core.c` | CRC32 и ограниченный предикат недоступности lag compensation |
| `src/nl_rage_math.c` | Предел команд, отдельные временные/вероятностные формулы, hits-to-kill, среднее, кнопки и подготовка движения; добавлены защитные условия, не полный оригинал |
| `src/nl_netvar.c` | Нормализованный поиск свойств, порядок поиска и нулевой sentinel; не ABI игрового объекта |
| `sdk/nl_sdk.h`, `nl_layouts.h`, `nl_report_records.h` | Частичные раскладки/типы/объявления; opaque-записи не означают восстановленную семантику |
| `sdk/nl_rage_math.h`, `nl_netvar.h` | Контракты существующих чистых функций |
| `sdk/inferred_signatures.h` | Автоматически выведенные сигнатуры в комментариях, не реализации |
| `tests/test_core.c`, `test_netvar.c`, `test_rage_math.c` | Переносимые тесты собственных функций; повторены обёрткой V7 |
| `tests/test_detours.cpp` | Windows-специфичный тест собственного target; здесь не запускался |

Запись N, её переходы и условный читатель в этих трёх `.c` отсутствуют.
V10 содержит плотную C/Python-модель обновления N и только конечный возрастной
предикат читателя. Она — опора ограниченного контракта, не готовый читаемый модуль.

## Связный вертикальный участок этого этапа

| Шаг | Новая реализация | Доказательства | Проверка |
|---|---|---|---|
| 1. Хранилище | `PositionRecord`, `PositionStore` | `412C2F20..412C2FF9`, шаг `74`, блок `3A000` | Раскладка и все начальные записи |
| 2. Разрешённое обновление | `update_resolved_record` | `4150B3AC..4150B3DE`, `4150B556..4150B777` | Отказы без записи, порядок снимка, знаковые сравнения, маски, дробные границы |
| 3. Метаданные | `store_resolved_item_definition` | `414F8552..414F85A4` | Ноль, положительный/отрицательный WORD, отсутствие объекта |
| 4. Условный читатель | `read_resolved_record` | `4150BE8F..4150BEC7`, `4150C19F..4150C1A9`, `4150C47F..4150C4F5` | Ранние выходы, оба переключаемых параметра, NaN, точная граница 4 |
| 5. Вход потребителя | `passes_item_consumer_gate` | `413650D2..413650F7` | Связный сценарий update → metadata → read → gate; отказ при устаревании |
| 6. Проверка | `tests/`, `Makefile` | Образ по SHA-256 и локальные байтовые якоря | Обычная сборка, ASan/UBSan, свежий objdump |

Шаги не требуют предположить результат неизвестного вызова. Внешние наблюдения
передаются аргументами; успешное прохождение окружающих неизвестных ветвей —
явная предпосылка, а не удаление этих ветвей из полного оригинала.

## Следующие кодовые участки (не выполнены этим этапом)

1. Источник и переходы маркера N+48 и метаданных в `414F8330`, затем полный
   потребитель `414FD800`: сохранить каждую охранную/перекрывающуюся ветвь.
2. Соединить имеющиеся контракты читателя битов/координат с полным форматом
   входного сообщения; не отождествлять отдельный разобранный tuple с пакетом.
3. Отдельный типизированный модуль T: агрегирование V7, настройки V8 и доказанный
   потребитель второго порога. Не использовать N для закрытия T+68.
4. Первые положительные источники Point+26/T+F4/прежнего +BC и критичные внешние
   привязки остаются отдельными исследованиями, без назначения кандидата наугад.

Ни один из этих пунктов не объявлен фоновым заданием или обещанием работы после ответа.
