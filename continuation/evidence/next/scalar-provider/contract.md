# R03 — fallback-step: один writer ячейки, provider остаётся frontier

## Назначение и предел

Исполнитель `r03-fallback-sol`, модель `gpt-6.1-sol`; base
`fecb19440f91c9dddbb60247c386fe55ef4e0c92`. Назначение координатора —
`89ed8b83ad44b28853679e18119a1518c469b6ac`, не устаревший `ready` в base.
Worktree `/tmp/hoplite/232-r03-fallback-sol`, ветка
`hoplite/sikyon-46eee495--r03-fallback-sol`. Область записи — только этот каталог;
C01, R01, C/C++-код, общий реестр/status/Makefile не изменяются.

Выбрано ровно наблюдение binary32 `[P_read + 0x24]`, где `P_read` — DWORD,
заново прочитанный из `0x4252194C` при `0x41C784D8`. После инвентаря прямых
литеральных ссылок выбран один writer: `0x41C5E404`. Другой writer включён
только как инструкция инвентаря, его upstream/downstream не исследуется.
Критерий остановки — одна непосредственная цепочка либо точный frontier;
здесь достигнут **frontier, не закрытие R03/GAP04**. Tolerance не исследуется.

`fallback_provider.json` закрепляет whole-image SHA256, шесть источников,
пять окон с SHA256/байтами и свежими декодами, а также хеш `direct_refs.tsv`.

`682ce73b371349f87da6fd9365f8550e240dcdb97951e80445e70286275ad96e`.
Соглашение адресации raw: VA = offset + `0x412A0000`, **не runtime-base**.
Архивный `functions/41C784B0.c` — только подсказка, решают байты/objdump.

Из корня Git:

```sh
python3 -B continuation/evidence/next/scalar-provider/verify_fallback_provider.py \
  --handoff /absolute/path/RAGEBOT_HANDOFF_V10
python3 -B continuation/evidence/wave2/gap04/verify_scalar_helper.py \
```

Нужны Python 3.10+ и GNU objdump с i386; дополнительных пакетов нет. Новый

номинированных инструкций и четыре кодовых окна. Пятое окно — данные ячейки.
Запускаются только собственный Python и objdump, никогда сам image.

## Инвентарь ровно одной ячейки

Полный raw-поиск байтов `4c195242` дал **767** совпадений. Таблица содержит
отдельные адреса operand/instruction, bytes, classification и fresh decode.
Из них 759 — MOV-чтения, 2 — CMP-чтения, 4 — ADD-чтения, 2 — записи:

| Номинированная инструкция | Байты | Локальный эффект |
|---|---|---|
| `0x41C5DC06` | `c7054c19524200000000` | DWORD `[0x4252194C] = 0` |
| `0x41C5E404` | `89354c195242` | DWORD `[0x4252194C] = ESI` |

Это исчерпывающий **инвентарь литерала в данном файле**, не полная карта
исполняемого кода/CFG. Начала всех 767 инструкций номинированы по соседнему
opcode/ModRM и проверены objdump с этих начал; глобальная достижимость и
границы инструкций каждого произвольного места не доказаны. Для выбранного
writer есть отдельное непрерывное окно от локального пролога `0x41C5E3B0`.
Отсутствие дополнительных литеральных stores не доказывает отсутствие
alias/computed-address/косвенных/внешних писателей. Четыре нулевых байта самой
ячейки в raw-image — снимок данных, не доказательство начального runtime-state.

## Единственная выбранная цепочка `0x41C5E3B0..0x41C5E40A`

Все операции ниже условны: управление дошло до них без исключения/fault.
Предметный тип, владелец и время жизни памяти не назначены.

1. `0x41C5E3C8`: отдельное чтение DWORD ячейки в EAX (`P_before`). Если оно
   ненулевое, `0x41C5E3D1` увеличивает DWORD `[P_before+0x380]`. Это не говорит
   ничего о значении ячейки при более позднем сравнении или fallback-чтении.
2. `0x41C5E3D7/3DD`: `push DWORD [0x42521948]`, затем `push 0x4940`;
   `0x41C5E3E2`: `call DWORD [0x4226723C]`. Цель indirect call не установлена;
   число `0x4940` не превращается в доказанный размер/тип объекта или allocator.
3. После возврата `0x41C5E3EB/3ED` копируют EAX в ESI и ECX;
   `0x41C5E3EF` делает `push EBX`, а `0x41C5E3F0` вызывает `0x41C5BDA0`.
   Rel32 проверяется отдельно. Затем `0x41C5E3F5` пишет DWORD EDI по
   `[ESI+0x493C]`, используя **послевызовный** ESI.
4. `0x41C5E3FB`: новое чтение `[0x4252194C]` сравнением с нулём (`P_compare`).
   `JNE 0x41C5E40A` пропускает store. Если сравнение видело ноль и исполнение
   продолжилось по fallthrough, `0x41C5E404` сохраняет послевызовный ESI в
   ячейку. Это обычный MOV, **не atomic compare-and-swap**.

Пролог `0x41C5BDA0..0x41C5BDC9` сохраняет ESI на стек, но внутри сам меняет
его на ESP. Просмотр пролога **не доказывает восстановление ESI на всех
выходах** или контракт вложенных вызовов. Поэтому происхождение записанного
ESI от EAX indirect call подтверждено только **при дополнительной предпосылке
сохранения ESI вызовом 0x41C5BDA0**. Эта предпосылка не объявлена фактом.
Полная реконструкция callee и indirect provider не проводится.

## Потребитель и точная недостающая связь

`0x41C784B0..0x41C784E3` подтверждает: равенство/unordered текущего и target
возвращает адрес без fallback. Иначе ordered `requested_step >= 0` обходит
fallback; отрицательный/unordered шаг достигает `0x41C784D8`:

```text
41C784D8: 8b0d4c195242  mov ecx,DWORD PTR [0x4252194C]  ; P_read
41C784DE: f30f105124    movss xmm2,DWORD PTR [ecx+0x24]
```

Это новое чтение указателя, затем 4-байтного float; значения, знак, NaN и
положительность provider здесь не установлены. Никакой null-защиты или
подмены отсутствующего provider нулём к оригиналу не приписано.

**Frontier:** один статический writer ячейки найден, но нет доказательства,
что именно он выполнился до этого fallback и что записанный указатель остался
тем же. `P_before`, `P_compare`, ESI при store и `P_read` не отождествляются.
Ни последовательность вызовов, ни dominance, lifetime, aliasing, runtime
binding, contents/writer поля `+0x24` не установлены. Каждый повтор helper,
включая разные marker/actor-компоненты, требует независимого наблюдения во
времени; совпадение абсолютного адреса этого не отменяет.

Следующий ограниченный шаг требует нового задания: либо полный контракт
сохранения ESI у `0x41C5BDA0`, либо статическое происхождение indirect target
`[0x4226723C]`. Даже их разрешение само по себе не установит writer-before-read
или источник float `+0x24`. Нет C17-заглушки provider, оригинальной загрузки,
исполнения/эмуляции, game/process/injection-доступа или закрытия полного GAP04.
