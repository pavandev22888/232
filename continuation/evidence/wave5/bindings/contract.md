# W5-BINDINGS: границы entity / weapon, один статический handle-путь

База: `3e5fd5f8f1ac3dadd635d19ed8b946ee2567fd3b`. Назначение W5-BINDINGS
из coordinator assignment `dada7f0`: только эта папка, GAP04 остаётся open.
Это статический контракт/frontier, не реализация runtime provider.

## Источник и воспроизведение

`anchors.json` закрепляет SHA-256 12 источников, полные байты и свежую x86
декодировку двух полуоткрытых окон. Адреса `nl.bin` используют **условное**
`VA = file_offset + 0x412A0000`, не установленную базу загруженного модуля.

| Окно | File offset | SHA-256 |
|---|---|---|
| `413130E0..413131AF` | `730E0` | `57fad267f75fe3dafd332a7cd5a48729df0c03c78f5ef93395174332c7d6c6a2` |
| `414F8552..414F85AE` | `258552` | `fa6fa2098ee2c01dd17702dfc93f60b919d68440ede1b6228f2ca539f5d357c0` |

Из корня worktree, с read-only handoff:

```sh
HANDOFF=/tmp/hoplite/workspace/runs/handoff/RAGEBOT_HANDOFF_V10
python3 -B continuation/evidence/wave5/bindings/verify_resolution.py --handoff "$HANDOFF"
python3 -B continuation/evidence/gap04/check_bindings.py --handoff "$HANDOFF"
PYTHONDONTWRITEBYTECODE=1 make -C continuation check HANDOFF="$HANDOFF" BUILD=../runs/w5-bindings/build
```

Собственный verifier читает файлы, вызывает `objdump` как статический декодер
и проверяет только константную U32-алгебру. Он не интерпретирует оригинальные
инструкции, не исполняет/не загружает DLL, не читает живой процесс и не сканирует
сигнатуры. Native/ASan/UBSan относятся к неизменённым офлайн C++-модулям,
не к выполнению этого пути оригинала. Новый verifier не добавлен в общий Makefile:
интегратор должен запускать его явно.

## Единственная исследованная цепочка: `413130E0`

1. Входной ECX указывает на локальный DWORD handle. Начальный `FS:[30]`
   даёт p; DWORD-сумма `[p+A8]+[p+A4]+[p+B8]+[p+BC]+[p+64]` вычисляется
   по модулю 2^32. Константа из `41313112..41313135` сворачивается в `20`.
   `ROR EDX,20h` имеет эффективный count 0. При равенстве `4131313B: 74 27`
   ведёт на `41313164`. Ветка неравенства содержит изменения регистра/стека,
   `41313161: FA` (CLI), затем `41313162: FF E7` (JMP EDI). Это не обычный
   false/null-return. Её эффект и достижимость не восстановлены.
2. На ветке равенства только константные U32-операции `41313164..41313187`
   дают `Q=2CF551DC`. Это **константа, используемая как receiver**, а не
   доказанный адрес загруженного модуля, не содержимое pointer-cell и не адрес
   метода. Наличие валидного объекта по Q не установлено.
3. `4131318D..41313198` сначала выделяет DWORD стека (`push eax`), затем
   перезаписывает его DWORD из входного `[ECX]`, то есть H. `MOV EDX,[EAX]`
   читает vtable из `[Q]`; `MOV ECX,EAX` задаёт receiver Q;
   `FF 52 10` вызывает `DWORD[vtable+10]`. Q не нужно дополнительно
   разыменовывать для выбора receiver. Содержимое vtable/slot и реализация
   метода остаются неизвестными. По форме вызова нельзя назначать классу имя
   конкретного движкового интерфейса или объявлять его модуль-владельца.
4. Возврат EAX записывается в ESI в `4131319B`; после прямого helper-вызова
   `413131A2 -> 41DA7C5C` копируется обратно в EAX (`413131A7`), далее
   восстанавливается сохранённый ESI и выполняется RET (`413131AE`). Передача
   результата через этот helper условна на нормальный возврат с сохранением
   ESI; его тело/все исключительные выходы здесь не доказаны. Не делается
   отдельного полного ABI-утверждения по одному локальному return.

### Два вызова — две observations

`414F8567` и `414F8573` действительно вызывают один `413130E0` с адресом
одной локальной копии H. Пусть нормальные результаты — R1 и R2. Только R1
проверяется (`414F856C: 85 C0`). При R1=0 `414F856E: 74 37` уходит прямо
на `414F85A7`, обходя store N+1C. После R1!=0 выполняется **второй** вызов;
его R2 записывается в ESI и используется для чтения item WORD без собственной
проверки на ноль. Само тело callee не пишет входную cell H; метод получает
DWORD H по значению, не указатель на эту cell.
Но локальные байты не доказывают R1=R2, R2!=0, стабильность mapping/lifetime
между вызовами или отсутствие внешних alias/побочных эффектов.

Между R2 и чтением стоит отдельная TLS-ветвь `414F8595 -> 414F88FA`.
Store требует её fallthrough; исход/возврат альтернативной ветви не исследован.
При достижении `414F85A0: 0F BF 04 30` читается signed 16-bit, результат
знаково расширяется до 32-bit и записывается `414F85A4: 89 47 1C` в N+1C.
Нулевой WORD — значение 0; отсутствие результата R1 — пропуск записи,
а не обнуление старого item. Это не обещание отсутствия других побочных
эффектов всего enrichment/helper.

Существующий `store_resolved_item_definition` реализует **только** проекцию
этой записи из уже предоставленного optional WORD. Он не заменяет два вызова,
не гарантирует тождество R1/R2 и не закрывает entity/weapon providers.
Нового C++-кода или фиктивного provider здесь нет.

## Runtime-base: альтернативы не стали фактами

Все 16 исходных V6 строк сохранены в `anchors.json` без выбора победителя:
14 client и 2 engine. Для каждой действует только условное равенство
`hypothetical_base + (preferred - 10000000) = 289A6D60`.

| Прежний named-кандидат | RVA | Гипотетическая база | Прежняя структурная оценка |
|---|---|---|---|
| client `10876D60` | `876D60` | `28130000` | Обычный пролог и vector-float тело; сильнее структурно, не привязан. |
| client `103E6D60` | `3E6D60` | `285C0000` | Продолжение блока/обратная ветвь, отдельный вход не установлен. |
| client `10076D60` | `76D60` | `28930000` | Короткая обёртка с вызовом `108A6380`. |

Свежий запуск **существующего** `gap04/check_bindings.py` повторно проверяет
хеши четырёх образов, PE mapping/байты всех 16 строк и эти anchors.
Это не новые кандидаты и не наблюдение runtime. Дополнительная константа Q
из выбранного handle-пути также не сообщает module base и не отличает
геометрические альтернативы: доказанной общей принадлежности у адресов нет.
14 неоднозначных V5 сигнатур и 16 V6 external requirements — ещё два отдельных
инвентаря; они не тождественны 16 geometry-кандидатам и не закрыты.

## Доказанность и точка остановки

- **Доказано статически:** байты/декодировка, оба direct-call target,
  алгебра guard=20 и Q=2CF551DC, стековый DWORD H, receiver Q, vtable slot +10,
  раздельные R1/R2, skip при R1=0, ширина/знаковость локального store.
- **Условно:** нормальная ветка guard, корректные FS/TLS/metadata чтения,
  сохранение nonvolatile-регистров/нормальный возврат внешних вызовов,
  валидность N/R2 и доступность Q. Это предусловия, не синтетические значения.
- **Не разрешено:** supplier actor и index, concrete interface/slot target,
  module ownership/runtime bases, metadata offsets, mapping/lifetime/alias,
  guards/exceptional paths, реальная достижимость и scheduling.

Остановка после одного локального разрешающего callee и его двух существующих
callsite. Следующий допустимый отдельный шаг потребовал бы конкретного
статического источника vtable/slot `DWORD[DWORD[2CF551DC]+10]` либо независимой
relocation/module-связи. Отрицательного поиска нет; runtime scanner, hooks,
подключение/инъекция и эмуляция оригинала не предлагаются. Приёмка
интегрированного SHA и независимое ревью остаются обязанностью координатора.
