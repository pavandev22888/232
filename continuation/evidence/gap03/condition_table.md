# GAP03: локальный переход charge/release

Это условная офлайн-модель двух подтверждённых участков и их общего байта
состояния, не восстановление целой функции или игрового автомата. Образ из
handoff: `workspace/work/nl_handoff_2026-11-06/nl.bin`, SHA-256 и ссылки на
все источники записаны в `charge_state_evidence.json`. Для статической проверки
использовано смещение `VA - 0x412A0000`; это условная файловая адресация, не
утверждение о рабочей базе процесса.

## Условия выбранного среза

| Порядок | Наблюдение / условие | Переход или результат | Источник и предел |
|---|---|---|---|
| 1 | В `charge_gate` внешний вызов возвращает ненулевой `AL` | Записать `1` в байт `0x4223F42C`; при нуле эта ветка байт не очищает | `0x414F12CC..12DC`; ветка set-only только в этом месте. Другие писатели/сбросы и срок жизни байта не закрыты. |
| 2 | Знаковый `raw_limit < 17` | `cap = raw_limit`, иначе `cap = 17` | `0x414F12E2..12EA`, `CMOVL` — знаковое условие. |
| 3 | `raw_limit == 0` | Перезаписать `cap = 59`; ноль не означает выключение | `0x414F12ED..12F7`. |
| 4 | `mode != 0` | `release = (cap >= 2 ? cap : 1) - 1`, арифметика DWORD | `0x414F1303..1316`; сравнение знаковое. |
| 5 | `mode == 0` | `release = (cap >= 3 ? cap : 2) - 2`, арифметика DWORD | `0x414F1318..1326`; сравнение знаковое. |
| 6 | `cap >= 4` | Начальный потолок `allowed = cap - 2`, иначе `1` | `0x414F1342..134A`. |
| 7 | Всегда после начального потолка | `requested = release - configured_count + 1` с оборачиванием по 32 битам; выбрать signed min(requested, потолок) | `0x414F1331..1353`; `configured_count` берётся через внешний индексированный объект и здесь не разрешается. |
| 8 | Беззнаковое `release < 2` | `selected = 0` | `0x414F1359..135E`; это `JB`, не знаковое сравнение. |
| 9 | Беззнаковое `release >= 2` | Начать с `selected = allowed` | `0x414F1359..1375`. |
| 10 | `use_allowed_limit != 0` | Оставить `selected = allowed` | Условие — байт/табличное значение `0x414F1360..1375`; его смысл и поставщик не разрешены. Имя аргумента структурное. |
| 11 | `use_allowed_limit == 0`, `mode == 0`, `option != 2` | `selected = max(trunc_toward_zero(cap / 2), 0) + 1` | `0x414F1377..13BD`; `option` получен из внешнего объекта. |
| 12 | Иначе при `use_allowed_limit == 0` | `selected = min_signed(cap >= 3 ? cap - 2 : 1, release)`; `cap - 2` и сравнения сохраняют DWORD/знаковую семантику | `0x414F1398..13AB`; последний DWORD записан в `0x42241A3C` по `0x414F13BE`. |
| 13 | В малом helper: байт `A == 0` | Вернуть `true`, не проверяя остальные входы | `0x414F30C0..30C7`, затем `MOV AL,1; RET`. |
| 14 | `A != 0`, общий latch `L == 0` | Перейти сразу к `D`; вернуть `D != 0` | `L` — тот же адрес `0x4223F42C`, который ветка v5 устанавливает в строке 1. `0x414F30C9..30F3`. |
| 15 | `A != 0`, `L != 0`, `(current_counter - 1) mod 2^32 == previous_counter` | Вернуть `false` | `0x414F30D2..30E1`; `DEC` выполняется в DWORD. |
| 16 | Предыдущая проверка счётчиков не совпала, `C != 0` | Вернуть `false` | `0x414F30E3..30EA`. |
| 17 | Остальные пути | Вернуть `D != 0` | `0x414F30EC..30F9`. Значения `A`, `C`, `D` оставлены структурными; их назначение не домысливается. |

В `advance_charge_state` вход `mode_result` используется для capacity-ветки и
локального set-only обновления `L` до расчёта лимитов. Затем модель оценивает
малый helper на том же snapshot `L`. Байты доказывают связь через адрес и
порядок set-before-capacity, но сохранённые обходы **не** доказывают, что этот
helper вызывается далее в том же runtime-пути или именно в таком порядке.
Композиция — именованный модельный шаг, а не восстановленный call graph.

## Оставшиеся внешние guards и фронтир

- До выбора `raw_limit` есть TLS/FS-контекст, чтение через TLS-слот и знаковый
  переход на `0x414F1C72` (`0x414F1268..1293`). Их операнды динамические.
- Получение `raw_limit` зависит от вызовов `0x41B6CF80` / `0x41B69220`; на
  альтернативной ветке `0x414F12C4` вызывается непрямой слот `[eax+0x34]`.
  Эти поставщики не моделируются. Другой вызов `0x41B6CF80` выдаёт событие
  `mode_result` для строки 1; его внутренний контракт неизвестен.
- `configured_count`, `option` и `use_allowed_limit` читаются из объектов,
  указателей и байтов таблицы. Полная идентичность полей/режимов, доступность
  памяти, исключения и все предшествующие проверки не доказаны.
- Обход v5 помечает непрямой `JMP EDI` в `0x414F1D07`; v8 branch frontier
  сохраняет его вместе с декодированными перед ним данными, не доказывая
  безопасную отсечку. В release-walk из v2 также остаются непрямые/дальние
  переходы `0x415E0154`, `0x415E0464`, `0x415E0606`, `0x415E0763`.
- Условные обходы — over-approximation обеих сторон, вызовы не проходятся.
  Нет доказательства достижимости, полного состояния DT/HS, завершения
  автомата или независимого аудита. Никакие opaque-guards не удалены.
