# GAP04, wave 2 — ограниченный скалярный helper 0x41C784B0

## Область и источник

База исследования — `ed9df79c028e63ca56fc191a226f5fe2f221df64`.
`scalar_helper.json` закрепляет SHA-256 полного `nl.bin`, байты и хеш каждого
диапазона, свежие инструкции GNU objdump 2.42, константы и хеши прежних
callee/caller-материалов. Условный raw-base `0x412A0000` — соглашение адресации
файла, не наблюдавшаяся база загруженного модуля. PE-привязка здесь не нужна:
пять локальных `E8 rel32` в том же файле ведут в одни и те же байты helper’а.

Прежний декомпилят `functions/41C784B0.c` использован только как подсказка.
Его `a7 < 0` неполно: свежие `UCOMISS/JAE` требуют fallback также при NaN.
Нулевой адрес `MEMORY[0x24]` из псевдокода не принят за реальное обращение:
байты сначала читают указатель из `0x4252194C`, затем float по `pointer+0x24`.

## Контракт, подтверждённый байтами

На входе cdecl относительно ESP до первого исполнения helper’а:

| Смещение | Значение | Новый интерфейс |
|---|---|---|
| `+04` | адрес читаемого/записываемого float; тот же адрес возвращается в EAX | `float& value` |
| `+08` | целевое значение | `target` |
| `+0C` | делитель шага | `divisor` |
| `+10` | нижний выбираемый предел | `lower_bound` |
| `+14` | верхний выбираемый предел | `upper_bound` |
| `+18` | порог абсолютной разности | `tolerance` |
| `+1C` | запрошенный шаг | `requested_step` |

1. `0x41C784BE..C3`: равенство **или unordered** текущего и целевого значения
   возвращает исходный адрес без записи. Поэтому NaN и знак нуля прежнего
   значения не нормализуются; fallback в этом случае не требуется.
2. `0x41C784C4..E3`: ordered `requested_step >= 0` использует переданный шаг.
   Иначе читается `[*(0x4252194C)+0x24]`. В новом API это `fallback_step`;
   отсутствие наблюдения даёт `fallback_step_missing`, не выдуманный float.
   Чтение находится **до** проверки порога, даже если потом будет snap к target.
   Сам fallback повторно не проверяется на знак/NaN.
3. `0x41C784E3..F7`: `delta = target - old`; модуль берётся маской `0x7FFFFFFF`.
   Если `abs(delta) <= tolerance` **или сравнение unordered**, пишется target
   без ограничений lower/upper.
4. `0x41C784F9..0x41C78527`: при строгом превышении порога отдельными binary32
   операциями вычисляется `candidate = ((step * delta) / divisor) + old`.
   Сначала сохраняется `upper < candidate`, затем исполняется
   `MAXSS(candidate, lower)`, затем по сохранённому сравнению выбирается upper
   либо результат MAXSS. MAXSS выбирает **второй** операнд при равенстве и NaN.
   Это не `std::fmax` и не общий `std::clamp`: при `lower > upper` результат
   может превысить upper. Проверка NaN и знака нуля не удалена.

`update_resolved_scalar` реализует эти значения и сообщает выбранную ветку,
но не воспроизводит исходный ABI, регистры, memory faults или FP exception flags.
Предпосылки: IEEE binary32 с округлением к ближайшему, без FTZ/DAZ, fast-math
и слияния арифметики; signaling NaN и наблюдаемые FP traps/flags вне области.
Делитель 0, инверсия границ и quiet NaN не заменены защитными значениями.

## Передача наблюдений в существующую модель N

### N+50 и N+54

Свежий диапазон `0x414F871F..0x414F8798` сохраняет исходную базу N, вычисляет
адреса `N+50/N+54` и передаёт их helper’у. **Текущие** значения читаются из
прежних полей N; mode/side54-seed задают **targets**, не исходные значения.

| Вызов | Поле | target | divisor | lower | upper | tolerance | requested_step |
|---|---|---|---|---|---|---|---|
| `0x414F8753` | N+50 | переданный seed XMM0 | 0.25 | 0 | 1 | binary32 0.01 | -1 |
| `0x414F877A` | N+54 | сохранённый seed XMM3 | binary32 0.025 | 0 | 1 | binary32 0.01 | -1 |

Значения четырёх средних float передаются из проверенных блоков констант
`0x4209BA60` и `0x4209BAA0`. Для каждого фактически нужного вызова нужен
отдельно разрешённый fallback: общая точка чтения не доказывает неизменность
наблюдения между вызовами. Результаты можно передать существующему
`produce_resolved_validity_marker` как `MarkerSideValues`; тест проверяет именно
эту композицию на синтетических значениях. Автоматическая интеграция/изменение
общего модуля в GAP04 не выполняется.

### N+30/N+34/N+38

Свежий диапазон `0x414FD938..0x414FDA4C` показывает три независимых вызова
для старых компонентов `N+30/+34/+38` с targets из `N+24/+28/+2C`.
Все три используют divisor с битами `0x3DAE147B` (binary32 0.085), нижнюю/верхнюю
границы `-FLT_MAX/+FLT_MAX`, requested_step `-1`. Tolerance каждый раз читается
из `[*(0x4223CA04)+0x14]`, а fallback выбирается внутри helper’а, как выше.
Эти адреса не связываются с runtime-владельцами. Тест одной оси задаёт оба
наблюдения явно; три helper-вызова не объявлены доказанным полным consumer’ом.

## Воспроизведение

Из корня репозитория, без записи в handoff/input/work:

```sh
python3 continuation/evidence/wave2/gap04/verify_scalar_helper.py \
  --handoff runs/handoff/RAGEBOT_HANDOFF_V10
make -C continuation BUILD=../runs/wave2/gap04/build \
  ../runs/wave2/gap04/build/test_resolved_scalar_helper \
  ../runs/wave2/gap04/build/test_resolved_scalar_helper_sanitize
runs/wave2/gap04/build/test_resolved_scalar_helper
ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1 \
  runs/wave2/gap04/build/test_resolved_scalar_helper_sanitize
```

Verifier только читает файлы, вызывает objdump для декодирования как binary-data
и выводит результат; не создаёт даже временные файлы. Старые журналы/доказательства
не переписываются. Новый тест подхватывается существующим Makefile wildcard.

## Граница доказательства

Получено реальное тело локального helper’а вместо двух/трёх произвольных
результатов внешнего поставщика. На его прямой ветке внешних чтений нет;
на fallback-ветке неизвестное чтение представлено явным аргументом.
Полные upstream seeds/guards, идентичность владельцев, настройка tolerance,
достижимость, другие писатели и runtime FP-окружение по-прежнему не доказаны.
Статические тесты собственной модели не являются выполнением оригинала
или независимым аудитом эквивалентности.

Названия trace/geometry в старом GAP05 не доказывают семантику: этот helper
работает с одним float и не выполняет геометрический trace. Старые имена
и общие модули здесь не меняются. Другой адрес `0x289A6D60` не назначен модулю,
список его PE-кандидатов не повторён как новый результат. Исходные DLL не
загружались, не запускались и не эмулировались; runtime/game/injection не было.
