# Протокол работы с разными агентами

Не нужны история чата, конкретный поставщик модели или прежние локальные пути.
Один агент может быть координатором; исполнители и рецензенты получают одинаковый
пакет документов, но **разные задачи и каталоги записи**.

## 1. Назначение

Координатор читает [TASKS.json](TASKS.json) и текущее состояние удалённой ветки.
До старта фиксирует в записи задания:

- `owner`, `status: in_progress`, точный `base_commit`;
- `worktree`, `branch`, фактические `write_paths`;
- ограниченную гипотезу/контракт, зависимости и критерии приёмки из карточки.

`ready` означает готовность взять **ограниченную работу**, не готовность всей
функциональности. `blocked` требует нового конкретного основания; нельзя
переименовать неизвестное в доказанный контракт. Запись реестра — координация,
не распределённая блокировка: второй координатор сначала синхронизируется
с владельцем, а не назначает того же исполнителя по старому клону.

Статусы: `ready`, `in_progress`, `blocked`, `review`, `done`.
`done` относится только к сформулированному результату карточки. Полные GAP-ID
живут отдельно в `continuation/STATUS.json` и не закрываются автоматически.

## 2. Изоляция

Команды выполняет координатор из **существующей рабочей ветки**, не из `main`:

```sh
BASE=$(git rev-parse HEAD)
BRANCH=$(git branch --show-current)
test -n "$BRANCH" && test "$BRANCH" != main
TASK=c01-scalar-agent1  # уникальный суффикс назначения
WORKTREE="$(dirname "$PWD")/232-$TASK"
git worktree add -b "${BRANCH}--${TASK}" "$WORKTREE" "$BASE"
```

Отдельные worktree дают отдельный index/HEAD/build, но общие refs Git.
Не используйте одну ветку одновременно в разных worktree. Не удаляйте чужой
worktree и не запускайте параллельно два задания с пересекающимися write paths.
Handoff можно разделять **только на чтение**, передавая абсолютный `HANDOFF`.
Новые логи и build остаются в worktree конкретного исполнителя.

Перед первой записью исполнитель проверяет `pwd`, `git status`, `git rev-parse HEAD`
и применимые `AGENTS.md`. При несовпадении базы сообщает координатору.
Исполнителю не назначаются корневые README/AGENTS, общий status, task registry,
Makefile и общие решения вместе с другим владельцем. Такие изменения интегрирует
координатор после обсуждения интерфейса.

## 3. Работа и точка остановки

1. Прочитать относящиеся к задаче код, контракты и доказательства; не повторять
   всю историческую реконструкцию и уже опровергнутые гипотезы без новых данных.
2. Сформулировать наблюдение, предусловия, идентичность объекта, ширину и порядок
   операций. Для неизвестного источника назвать конкретный frontier.
3. Добавить связный код/тесты **либо** результат ограниченного исследования.
   Не создавать пустые модули ради видимости продвижения.
4. Запустить узкие проверки, проверить diff, сделать коммит только своих файлов.
   Не выполнять push, merge, rebase родительской ветки или чужой cherry-pick.
5. Вернуть отчёт по шаблону ниже. Остановиться по достигнутому результату или
   доказанному блокеру, не расширять задание бесконечно.

Если агент не может выполнить назначение из-за разрешений, возможностей или
своих ограничений, фиксируется невыполненное задание. Не менять модель/маршрут
для обхода ограничений; координатор выбирает отдельную допустимую работу.

## 4. Отчёт исполнителя

```text
Task ID / scope:
Base SHA / result SHA / worktree / branch:
Changed paths:
Source files + SHA256 + address/byte anchors:
Confirmed local claims:
Model assumptions / hypotheses / unknowns:
Commands, working directory, tool versions, exit codes:
Logs and evidence paths (relative to repository):
Coverage and tests not run, with reasons:
Input/work unchanged check:
Acceptance result: ready for review | blocked (not done)
Exact remaining frontier and suggested next bounded step:
```

Не включать секреты, полное окружение, приватные записи или оригинальные DLL.
Публикуемые логи сначала просматриваются. SHA тестируемого кода и хеши отчётов
позволяют отличить реальное выполнение от пересказа старого PASS.

## 5. Интеграция и независимая проверка

Координатор проверяет область diff и доказательства, переносит принятые коммиты
в ветку задачи, затем запускает полный `make check` с доступным HANDOFF.
После интеграции фиксирует SHA и создаёт **новый** worktree рецензента от него.
Рецензент не меняет код и не считает отчёт автора доказательством успешного прогона.

Проверяются отдельно:

- семантика и соответствие байтовым основаниям, недоказанные предпосылки;
- тесты, воспроизводимость, sanitizer diagnostics, неизвестные ветви;
- для C-порта — реальная C17-сборка и отсутствие зависимости C-библиотеки от C++.

После исправления замечаний проверяется новый SHA. Провалившийся лог сохраняется
с истинным статусом; проверка не пропускается ради зелёного отчёта.
Обновляются `STATUS.json`, `TASKS.json`, `DECISIONS.md`, source index при изменении
карты и новые evidence. Старые acceptance-отчёты не переписываются задним числом.

## 6. Передача и публикация

Координатор делает commit/push в существующую ветку и обновляет описание PR
при изменении его содержания. До нового указания пользователя PR не сливается,
не ставится в очередь и auto-merge не включается. Проверяются опубликованный SHA,
живые checks и обсуждения; отсутствие CI нельзя называть зелёным CI.

Для следующего агента достаточно URL ветки/PR, SHA, Task ID и
[универсального промпта](AGENT_PROMPTS.md). Для возобновления незавершённой задачи
нужны ещё последний commit/evidence и её точный frontier, а не весь разговор.
Модель не зафиксирована протоколом; прежние `gpt-6.1-sol` относятся к журналу W3–W4.
Не заявлять effort/fast-настройки, если интерфейс запуска их не предоставлял.
